# Installation и локальные настройки

[README](../README.md)

Это инструкция по существующему коду, а не отчёт об успешной установке. Проверенные версии Windows, PowerShell, Docker Desktop, Minikube, Kubernetes и CNI пока не опубликованы.

## Перед запуском

1. Выберите отдельную лабораторную среду Windows с Docker Desktop в режиме Linux containers. Не используйте общий кластер: скрипт меняет сетевые правила ноды и напрямую обращается к контейнеру `minikube`.
2. Установите `minikube` и `kubectl`, обеспечьте доступ к registry для загрузки закреплённого webtop-образа. Конкретные версии сначала зафиксируйте; эта документация их не назначает проверенными.
3. Для новой ноды конфигурация задаёт 4 CPU и 6144 MB памяти. Выделите дополнительную память Docker Desktop и Windows. Суммарные limits четырёх сред выше 6 GB; запас под нагрузку не измерен.
4. Для существующего стенда сохраните настройки и получите проверенные Windows-копии backup до любых изменений, способных пересоздать контейнеры. Проверка backup описана в [кейсе](cases/backup-recovery.md).

Read-only проверки, выполняемые вручную в PowerShell:

```powershell
$PSVersionTable.PSVersion
docker version
minikube version
minikube profile list
minikube status
kubectl version --client
kubectl config current-context
```

Если текущий context или профиль относится к другому проекту, не запускайте лабораторные скрипты до выяснения. Код использует текущий context `kubectl` и имя Docker-контейнера `minikube`, не изолируя их явными параметрами.

## Настройки

Скрипты создают `lab.config.ps1` из `lab.config.example.ps1`, если локального файла нет. Его можно заранее скопировать вручную и проверить. Он исполняется как PowerShell-код: используйте только доверенный файл. Существующий файл не заменяйте шаблоном.

| Параметр | Назначение и значение по умолчанию |
|---|---|
| `$MinikubePath`, `$KubectlPath`, `$DockerDesktopExe` | Пусто: поиск в PATH/типичных каталогах |
| `$ServerPort`, `$ClientPorts` | 3000 и 3001/3002/3003; ровно три клиентских порта |
| `$BindAddress` | `127.0.0.1`; оставьте локальный доступ |
| `$MinikubeCpus`, `$MinikubeMemory` | 4 и 6144; влияют на создание ноды |
| `$ServerServices` | `mariadb`, `apache2`, `zabbix-server`, `zabbix-agent` |
| `$ClientServices` | `zabbix-agent` |
| `$BackupDir` | Пусто: `backups/` относительно проекта |

Сети определены в `$LabSubnets` в `lab-common.ps1`. Их изменение — изменение работающей сети, не настройка документации.

## Запуск — изменяет состояние стенда

Из корня репозитория:

```powershell
.\start-debian.ps1 -NoBrowser
```

Или откройте `start-debian.bat`. Если политика Windows запрещает скрипты, сначала выясните локальные требования; не отключайте её глобально ради лаборатории. BAT-обёртка запускает PowerShell с `ExecutionPolicy Bypass` для своего процесса.

Скрипт применяет оба манифеста, восстанавливает состояние, меняет сеть, патчит hostname и webtop/nginx, запускает установленные сервисы, выполняет сетевой self-test и port-forward. Он **не устанавливает** MariaDB, Apache, Zabbix server/frontend/agent. Отсутствующий сервис пропускается; итоговый SUCCESS сам по себе не доказывает готовность мониторинга.

Ожидаемые GUI: localhost:3000–3003. Окно запуска оставьте открытым. `/zabbix` требует отдельной настройки приложений.

## Проверка после запуска

В другом PowerShell-окне:

```powershell
kubectl get deployments,pods,services -n debian-lab
kubectl get events -n debian-lab --sort-by=.metadata.creationTimestamp
```

Проверьте четыре Pod, итог скрипта, доступность GUI и предусмотренный сетевой self-test. Сервисы и мониторинг проверяются отдельно по [кейсам](cases/linux-services.md). Запишите реальные версии, дату, результаты и отклонения в [реестр доказательств](evidence/README.md).

## Сохранение, остановка, повторный запуск

`save-state.bat` / `.ps1` сохраняет writable state и экспортирует архивы. `stop-debian.bat` / `.ps1` предлагает сохранение и stop/pause Minikube. Сохранение создаёт краткий перерыв для сервисов БД; pause не освобождает память. Само наличие архива не гарантирует восстановления.

После пересоздания Pod текущая процедура предусматривает повторный `start-debian`, который меняет состояние. Сначала изучите диагностику и убедитесь, что backup пригоден.

Удаление Minikube, сброс Docker Desktop, обновление digest, изменение YAML или перенос на PVC не входят в обычную установку существующей лаборатории. Для них нужен отдельный план с проверкой backup, окном простоя и условиями возврата.

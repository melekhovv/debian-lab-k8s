# Инженерные решения и компромиссы

[README](../README.md)

Документ объясняет текущую реализацию по коду. Это последующее описание её свойств, а не выдуманная история выбора технологий или выполненных миграций.

| Решение в коде | Что даёт | Цена и ограничения |
|---|---|---|
| Debian webtop в Kubernetes | Четыре доступные через браузер среды и единый жизненный цикл Deployment | Общий kernel, накладные расходы GUI; это не моделирование четырёх полноценных VM |
| Образ по digest | Однозначная версия базового файлового слоя | Не даёт автоматических security updates; обновление требует проверки патчей webtop и совместимости backup |
| ClusterIP и loopback port-forward | Не нужен внешний Ingress/NodePort для локальной работы | Окно сопровождения должно работать; ClusterIP не закрывает доступ изнутри кластера |
| Policy routing на ноде | Принудительный маршрут через сервер поверх общей CNI-сети | Зависимость от veth, таблицы 100, приоритета 1000 и адресации; нет трёх изолированных L2-сегментов |
| NOTRACK для учебного трафика | Обходит описанную в коде проблему двойного прохождения conntrack | Отключает state tracking для затронутых потоков; причина и эффект требуют наблюдения на конкретном стенде |
| Сохранение upperdir | Может сохранить пакеты и настройки, изменённые внутри контейнера | Зависимость от overlayfs/containerd, базового образа и согласованности живых данных |
| Условный запуск services | Можно поднять уже установленные приложения после восстановления | Установка приложений не воспроизводится из Git; skip не равен работающему сервису |

## Ближайшие инженерные приоритеты

1. Фиксировать проверяемое окружение и фактические результаты вместо общих обещаний.
2. Автоматически выявлять регрессии в манифестах без доступа к рабочему кластеру.
3. Сохранить стабильный запуск, выделив read-only наблюдение в отдельную команду.
4. Проверять recovery только на изолированной копии; не использовать рабочие данные для демонстрационного эксперимента.

Проверка context перед изменениями, надёжная остановка/возврат БД, владение сетевыми правилами и перенос данных на постоянное хранение остаются отдельными задачами. Их нельзя представить уже реализованными через изменение README.
